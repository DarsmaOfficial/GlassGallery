## What changed

`PlayerScreen.kt:416` now calls `MediaStore.createTrashRequest(resolver, listOf(videoUri), true)`
instead of `createDeleteRequest`. Video deletion is recoverable, matching the photo viewer and the
gallery multi-select path. `player.pause()` added as the first statement so playback and audio stop
before the system sheet appears, matching the Trim button 30 lines above. The comment at :226-228
no longer misdescribes the behaviour.

The launcher was deliberately **not** changed. `removeFromList(setOf(videoId))` + `onBack()` stays
correct because a trashed row drops out of the default MediaStore query — proven by
`MediaStoreVideoSource.kt:169` needing an explicit `QUERY_ARG_MATCH_TRASHED = MATCH_ONLY` to see
trashed items at all.

## Review history — two rounds

**Round 1 (`3e3beca`):** Kotlin correct. Red-team passed it as "a strict improvement to a data-loss
path" and found the *guard* to be the weak half, with two HIGH false-PASS holes. Red-team had no
shell and said so; the conductor reproduced both with commands rather than accepting the argument:

- `Path.rglob` on a missing directory returns empty and raises nothing → the guard printed an empty
  inventory and exited 0, certifying a tree it never read.
- The `createTrashRequest` call spans two lines, so line-by-line scanning never saw the boolean.
  Injecting `true` → `false` left the guard printing `OK ... exit=0`. That typo is **worse than the
  original bug**: the OS shows an untrash confirmation, returns `RESULT_OK`, the launcher prunes the
  item and navigates back, so the video vanishes from the gallery **while remaining on disk**.

**Round 2 (`d077345`):** guard rewritten to join file text before matching, inspect the argument
list, distinguish exit 2 (guard broken) from exit 1 (code bad), and cover `resolver.delete` /
`deleteDocument` as failures plus `File.delete()` as report-only.

## Unverified — stated plainly

- **Nothing here was compiled, run, or rendered.** No JDK, SDK, Gradle, emulator or device.
- **The behavioural claim is untested:** that the video now lands in the OS bin and is restorable
  from the Trash screen. That needs a device.
- 🔴 **The comment's promise may be false for non-owned media.** The app holds only
  `READ_MEDIA_VIDEO`/`READ_MEDIA_IMAGES` — no `MANAGE_MEDIA`. MediaProvider may restrict
  trashed-row visibility for a non-owner app, in which case `TrashScreen` shows an empty bin for
  anything the app did not create. Even at worst the item remains recoverable via the system
  Files/Photos bin, which is strictly better than permanent deletion — but the comment states
  recoverability as fact and it is not established. **Highest-value device check.**
- The guard is **not wired into CI**. Nothing runs it automatically today.

## Deferred, recorded, deliberately not fixed here

Widening a data-loss fix turns one risk into several. All pre-existing:

1. `PlayerScreen.kt:197` has no `onPlayerError` listener; `VideoTrimScreen.kt:250` does. If ExoPlayer
   reopens the URI mid-trash it can freeze silently with no log.
2. `onDispose` saves a resume position even for a trashed item, so the store accrues rows for media
   that no longer appears, and a restored item resumes from a stale position.
3. "30 days" is OS-determined via `DATE_EXPIRES`, not guaranteed. The same wording appears at
   `TrashScreen.kt:132,147` — fix all four sites together or none.
4. The guard's regex still matches inside comments and string literals. Fail-safe direction, left.
