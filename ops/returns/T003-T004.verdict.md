## The finding

The project's stated invariant — *"a paid API is structurally impossible in a process that cannot
open a socket"* — **was false in every APK ever published.** It was only ever true of the source
manifest. Nothing had ever inspected the merged result.

CI run **#73** failed on the gate's first contact with a real APK:

| permission | origin |
|---|---|
| `READ_MEDIA_VIDEO`, `READ_MEDIA_IMAGES`, `READ_EXTERNAL_STORAGE` | declared |
| **`ACCESS_NETWORK_STATE`**, **`INTERNET`** | **merged in — banned** |
| `WAKE_LOCK`, `RECEIVE_BOOT_COMPLETED`, `FOREGROUND_SERVICE` | merged in, never requested |
| `…DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION` | AndroidX Core, app-scoped, signature-level |

Run **#74** after the repair: **both banned permissions gone, nothing else changed.** Verified by
reading the printed list, not inferred from the exit code.

## What did the finding

Not the denylist — the **evidence print**. The banned-list check would have caught the two network
permissions. It was the full permission list, printed on every run, that surfaced three more nobody
had asked for. That print existed only because red-team insisted a passing gate should show its work.

## Scope discipline

Only the two banned permissions were removed. `WAKE_LOCK` / `RECEIVE_BOOT_COMPLETED` /
`FOREGROUND_SERVICE` together look like a genuine scheduler component; stripping them could break
background behaviour no build can detect, and they are not the invariant. Filed separately.

The two `tools:node="remove"` directives are **separate elements by design**.
`ACCESS_NETWORK_STATE` is the riskier removal — a `ConnectivityManager` query without it throws
`SecurityException`, so library code that checks connectivity *defensively*, even for on-device work,
would crash rather than degrade. If ML Kit features crash on hardware, that directive can be
reverted alone while keeping the `INTERNET` removal.

## 🔴 Device verification — the one that matters now

`tools:node="remove"` deletes the permission from the manifest. It does **not** stop library code
attempting the operation. Nothing about runtime is proven.

**Exercise the ML Kit chain that contributed these permissions:** barcode scan, OCR text search,
image labelling, portrait background blur. Also the Glance favourites widget, since
`RECEIVE_BOOT_COMPLETED` / `FOREGROUND_SERVICE` point at a component in the same area.

If something crashes, `ACCESS_NETWORK_STATE` is the prime suspect and is revertible alone.

## What I got wrong

My 10-case local harness fed the script a **hand-written imitation** of `aapt2` output. It tested the
regex against my model of the format, not against aapt2 — the identical "validated against itself"
defect as the two guards before it, committed while I was explicitly claiming to have avoided it.
Red-team caught it. CI has now proven the parse against real output, but only for the
`uses-permission:` form.

I also briefly mis-read run #73's log as lacking the `DYNAMIC_RECEIVER` entry and nearly reported a
phantom "new permission appeared" finding. It was present in both runs; my extraction truncated.
Checked before reporting.
